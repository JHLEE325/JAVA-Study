## 예외처리

## 1. 자바에서 예외 처리 방법

### 자바에서 예외 처리란
자바의 예외 처리는 프로그램 실행 중 발생하는 비정상 상황(Exception)을 제어 흐름으로 처리하는 메커니즘

### try-catch
```java
try {
    int result = 10 / 0;
} catch (ArithmeticException e) {
    System.out.println("예외 발생");
}
```
동작흐름
1. try 블록 실행
2. 예외 발생 시 즉시 중단
3. 해당 타입의 catch 블록으로 이동
4. 이후 정상 흐름으로 복귀
- 여러 catch 가능 (상위 타입은 아래에 위치해야 함)

### finally
```java
try {
    // 로직
} catch (Exception e) {
    // 예외 처리
} finally {
    // 무조건 실행
}
```
특징
- 예외 발생 여부와 관계없이 항상 실행
- 주로 리소스 해제로 활용 (DB, 파일, 스트림)

### throw (예외 발생시키기)
```java
throw new IllegalArgumentException("잘못된 값");
```
특징
- 개발자가 명시적으로 예외를 발생
- 비즈니스 로직을 구현할 때 이를 검증하는 데에 자주 사용

### throws (예외 위임)
```java
public void readFile() throws IOException {
    // 예외 발생 가능
}
```
특징
- 예외가 발생 가능한 메서드 선언 시 throws로 위임하도록 작성
- 메서드가 예외를 직접 처리하지 않고 호출자에게 책임을 넘김
- Checked Exception에서는 필수

#### Checked Exception이란
컴파일 시점에 강제 처리되는 예외로, 대표적으로 IOException, SQLException, InterruptException 등이 있으며 <br>
주로 외부 자원이나 환경 의존적인 상황에서 발생 <br>

실무에서는 이러한 형태 보다는 catch를 통하 Checked Exception을 잡아서 Runtime으로 처리

### try-with-resources
```java
try (BufferedReader br = new BufferedReader(new FileReader("a.txt"))) {
    br.readLine();
}
```
특징
- AutoCloseable 구현 객체 자동 close
- finally 없이 리소스 해제 가능
- 실무에서 자주 사용

## 2. 자바가 제공하는 예외 계층 구조

### 예외 계층 전체 구조
```
Throwable
 ├── Error
 └── Exception
      ├── RuntimeException (Unchecked)
      └── Checked Exception
```

### 최상위 : `Throwable`
자바에서 모든 예외/에러의 최상위 클래스
- `throw`할 수 있는 대상은 전부 Throwable
- 두 가지로 분기됨
  - Error
  - Exception
 
### Error (시스템 레벨 문제)
대표 예시
- `OutOfMemoryError`
- `StackOverflowError`

특징
- JVM/시스템 수준 오류
- 개발자가 처리하는 것이 불가능
- 복구가 불가능

즉 애플리케이션 레벨에서 건드릴 영역이 아님

### Exception (개발자가 처리 가능한 영역)
일반적으로 말하는 예외가 Exception에 해당함 <br>
Checked Exception 과 RuntimeException으로 나뉨

#### Checked Exception
RuntimeException을 제외한 Exception
대표 예시
- `IOException`
- `SQLException`
- `InterruptedException`

특징
- 컴파일 시점에 체크됨
- 반드시 컴파일 시점에 처리가 되어있어야 컴파일됨
- 복구가 가능한 상황

#### RuntimeException
대표 예시
- `NullPointerException`
- `IllegalArgumentException`
- `IndexOutOfBoundsException`
- `ClassCastException`

특징
- 런타임 시 발생
- 컴파일러가 강제하지 않아서 처리 안해도 컴파일 됨
- 주로 프로그래밍 오류, 로직 오류에서 발생

#### 체크드 vs 런타임
| 구분     | Checked Exception | RuntimeException |
| ------ | ----------------- | ---------------- |
| 체크 시점  | 컴파일               | 런타임              |
| 처리 강제  | O                 | X                |
| 복구 가능성 | 높음                | 낮음               |
| 용도     | 외부 자원             | 개발자 실수           |

### 계층 구조를 이해해야 하는 이유
#### 1. catch 동작 원리
```java
try {
    ...
} catch (Exception e) {
}
```
위처럼 큰 범위의 Exception이면 하위 모든 예외가 다 catch됨

#### 2. 다형성 적용
```java
catch (IOException e)
catch (Exception e)
```
부모 타입으로 묶어서 처리가 가능

#### 3. catch 순서 중요
```java
catch (Exception e)
catch (IOException e) // 컴파일 에러
```
위에서 큰 범위로 catch 하면 아래에 닿지 않아서 컴파일 에러가 발생

## 3. Exception vs Error 차이

### 핵심 비교
Exception은 처리 가능한 문제, Error는 처리 불가능한 시스템적 문제
| 구분       | Exception   | Error              |
| -------- | ----------- | ------------------ |
| 발생 영역    | 애플리케이션      | JVM / 시스템          |
| 처리 가능 여부 | 가능          | 불가능                |
| 복구 가능성   | 있음          | 없음                 |
| 처리 방식    | try-catch   | 처리 안 함             |
| 예시       | IOException | OOM, StackOverflow |

### Error는 catch 하면 안되는 이유
```java
try {
    ...
} catch (Error e) {
    // Error를 catch 하지는 않음
}
```
이유
1. 이미 시스템이 망가진 상태
  - OOM -> 이미 메모리가 없음
  - StackOverflow -> 스택이 이미 붕괴되었음
  - catch하더라도 이미 정상 동작이 불가능함
2. 복구 불가능
3. Error를 catch하면 상태가 깨진 채로 계속 실행되어 오히려 더 위험

## 4. RuntimeException과 RE가 아닌 것의 차이
Checked Exception은 복구 가능한 상황, RuntimeException은 프로그래밍 오류

### 핵심 비교
| 구분     | Checked Exception | RuntimeException     |
| ------ | ----------------- | -------------------- |
| 체크 시점  | 컴파일               | 런타임                  |
| 처리 강제  | O                 | X                    |
| 원인     | 외부 환경             | 코드 오류                |
| 복구 가능성 | 높음                | 낮음                   |
| 예시     | IOException       | NullPointerException |

### 언제 RE를 쓰고 언제 CE를 써야할까?
#### Checked Exception을 써야 하는 경우
복구 가능한 상황
- 파일이 없는 경우 -> 다른 파일로 재시도 가능
- DB 실패 -> 이것도 재시도 가능
- 네트워크 실패 -> fallback 가능
  ```java
  try{
    file.read();
  } catch (IOException e) {
    retry();
  }
  ```

#### RuntimeException 써야 하는 경우
프로그래밍 오류 / 비즈니스 규칙 위반
- null 접근
- 잘못된 파라미터
- 상태 오류
  ```java
  if (user == null) {
    throw new IllegalArgumentException("user 없음");
  }
  ```

#### 실무에서 사용하는 방식
대부분 RuntimeException을 사용한다.
이유
1. throws를 남용하여 전파 후 처리 하는 것이 코드가 복잡해지기 때문
2. 스프링 트랜잭션이 RuntimeException만 롤백하기 때문
3. 계층 분리 원칙 (예외를 위임하지 않기 위해)
```java
try {
    file.read();
} catch (IOException e) {
    throw new RuntimeException(e);
}
```
위처럼 Checked Exception을 잡아서 RuntimeException으로 처리

## 5. 커스텀 예외 만드는 방법

### 커스텀 예외 사용 이유
- 의미 있는 예외 전달
- 예외를 도메인 중심으로 표현하기 위해
- 유지보수성을 향상시키기 위해서

예시
```java
throw new RuntimeException("에러");
// 무슨 에러가 발생했는지, 왜 발생했는지, 어디서 발생했는지 알 수 없음
throw new UserNotFoundException();
// 유저가 찾아지지 않았구나! 한눈에 알 수가 있음
```
### 기본 구현 방법
#### RuntimeException 기반 (실무에서 대체로 사용)
```java
public class UserNotFoundException extends RuntimeException {
    public UserNotFoundException(String message) {
        super(message);
    }
}

if (user == null) {
    throw new UserNotFoundException("유저 없음");
}
```

#### Checked Exception 기반 (거의 사용 안 함)
```java
public class FileProcessException extends Exception {
}
// 코드 복잡도의 이유로 잘 사용하지 않음
```

#### 생성자 패턴
```java
public class BusinessException extends RuntimeException {

    public BusinessException(String message) {
        super(message);
    }

    public BusinessException(String message, Throwable cause) {
        super(message, cause);
    }
}
```
- 원인 예외(cause) 유ㅜ지
- 디버깅 가능

#### 계층 설계 (실무 핵심)
공통 부모 예외
```java
public class BusinessException extends RuntimeException {
}
```
도메인별 예외
```java
public class UserNotFoundException extends BusinessException {
}

public class OrderNotFoundException extends BusinessException {
}
```
구조
```
RuntimeException
 └── BusinessException
      ├── UserNotFoundException
      └── OrderNotFoundException
```

#### Error Code 패턴
```java
public enum ErrorCode {
    USER_NOT_FOUND,
    INVALID_REQUEST
}
```
```java
public class BusinessException extends RuntimeException {
    private final ErrorCode errorCode;

    public BusinessException(ErrorCode errorCode) {
        this.errorCode = errorCode;
    }
}
```
장점
- 프론트에 명확한 에러 내용 전달 가능
- API 응답 표준화
- 메시지 분리 가능

#### 실무 흐름
```
Controller
  ↓
Service (예외 발생)
  ↓
Global Exception Handler
  ↓
Response 반환
```

### 좋은 예외 설계 기준
1. 의미 명확
2. 너무 많이 만들지 않기
3. 공통 부모 사용
4. 메시지 + 원인 포함
5. ErrorCode 활용
