## 제네릭(Generic)

## 1. 제네릭 사용법

### 제네릭의 기본 개념
제네릭(Generic)은 클래스, 인터페이스, 메서드가 사용할 타입을 “미리 고정하지 않고” 외부에서 결정하도록 만드는 문법
```java
List<String>
List<Integer>
```
위처럼 타입을 파라미터화 하는 기능 <br>
Java 5에서 도입
- 타입 안정성
- 불필요한 캐스팅 제거

### 제네릭이 등장한 이유
#### 제네릭 이전
```java
List list = new ArrayList();

list.add("hello");
list.add(10);

String s = (String) list.get(1);
// ClassCastException 발생
```
제네릭 등장 이전의 컬렉션은 모두 `Object` 기반으로 <br>
위처럼 꺼낼 때 문제가 발생
- 어떤 타입이 들어오는지 컴파일러가 모름
- 오류를 컴파일 시점에 파악 불가
- 런타임까지 문제가 숨겨짐

#### 제네릭 이후
```java
List<String> list = new ArrayList<>();

list.add("hello");
list.add(10); // 컴파일 에러 - 컴파일 시점에 검증 가능

String s = list.get(0);
// 다운캐스팅 제거 가능
```

### 제네릭의 기본 문법
```java
class Box<T> {
    private T value;

    public void set(T value) {
        this.value = value;
    }

    public T get() {
        return value;
    }
}

//사용
Box<String> box = new Box<>();
box.set("hello");

String s = box.get();
```

### 타입 파라미터
| 이름 | 의미      |
| -- | ------- |
| T  | Type    |
| E  | Element |
| K  | Key     |
| V  | Value   |
| N  | Number  |

### 제네릭 인터페이스
```java
interface Repository<T> {
    void save(T entity);
    T findById(Long id);
}

class UserRepository implements Repository<User> {
}
```
실무에서 흔히 사용하는 패턴
- Spring Data JPA
- MyBatis
- QueryDSL
- 각종 Repository 패턴

### Diamond Operator(`<>`)
Java 7부터 컴파일러가 우변의 타입을 추론하는 기능을 지원
```java
List<String> list = new ArrayList<String>();
// 7버전 이전에는 위처럼 타입 명지

List<String> list = new ArrayList<>();
// 컴파일러가 우변의 타입을 추론하여 자동 적용
```

### 제네릭과 다형성
```java
List<String> list = new ArrayList<>();
// 위를 지향하고 아래를 지양하는 이유

ArrayList<String> list = new ArrayList<>();
```
- 구현체 교체 어려움
- 결합도 증가
- 테스트 어려움
- 즉 인터페이스 기반 설계를 권장함

### 제네릭과 Primitive Type
제네릭에서 primitive type 사용이 불가능한 이유
```java
List<String>
List<Integer>

// 위 두가지는 런타임에는 List로 동작함
// 즉 내부적으로는 Object 기반 처리
```
primitive는 Object 상속이 불가능하고 참조 타입이 아니기 때문에 인자로 사용 불가능

### 제네릭의 장점
- 타입 안정성 : 컴파일 시 오류 검출 가능
- 캐스팅 제거 : 코드 간결성 증가
- 코드 재사용성 증가 : 하나의 코드로 여러 타입 처리 가능

### 제네릭의 한계
- 타입 소거 : 런타임 정보 부족
- primitive 사용 불가 : Wrapper 필요
- 문법 복잡성 : Wildcard, bounded type 등 난이도 존재

### 제네릭 주요 포인트
| 주제              | 핵심                       |
| --------------- | ------------------------ |
| 제네릭 목적          | 타입 안정성 + 캐스팅 제거          |
| Raw Type 문제     | 런타임 오류 위험                |
| Primitive 불가 이유 | Type Erasure + Object 기반 |
| 배열과 차이          | 배열=공변, 제네릭=불공변           |
| static 제한       | T는 인스턴스 시점 결정            |
| 핵심 철학           | 컴파일 타임 타입 안정성            |

## 2. 제네릭 주요 개념

### Bounded Type
타입 파라미터에 허용 가능한 범위를 제한하는 기능

#### Upper Bounded Type (`extends`)
```java
class Box<T extends Number> {
}
```
Number, Integer, Long, Double 같은 Number 계열 타입만 허용한다

#### 제한이 필요한 이유
```java
class Box<T> {
    T value;

    void print() {
        value.doubleValue(); // 안됨
    }
}
```
컴파일러는 `T`를 그냥 `Object` 수준으로 인식
> T가 String인지, Integer인지 모르기 때문

#### Bounded Type 적용
```java
class Box<T extends Number> {
    T value;

    double getDoubleValue() {
        return value.doubleValue();
    }
}
```
컴파일러는 최소한 Number 타입이라는 사실을 보장 받음 <br>
따라서 Number 메서드 사용 가능

#### 다중 Bound
클래스 + 인터페이스 조합 가능
```java
<T extends Number & Comparable<T>>
```
Number 계열이면서 Comparable 구현도 필요하다
```java
<T extends A & B> // X
<T extends Number & Serializable>
```
- 클래스는 하나만 가능
- 클래스가 먼저 와야 함

#### Bounded Type의 핵심 목적
1. 타입 제한 - 의도하지 않은 타입 차단
2. 특정 기능 사용 가능
3. API의 의도 표현

### Wildcard(`?`)
Wildcard는 알 수 없는 타입을 표현하는 문법
```java
List<?>
```
타입은 모르지만 어쨌든 List 이다

#### Wildcard 필요한 이유
제네릭은 기본적으로 불공변
```java
List<Object> list = new ArrayList<String>(); // X
```
실제 개발에서는
- List<String>
- List<Integer>
- List<User>
모두 받고 싶은 경우가 있는데 그 때 사용

#### Unbounded Wildcard
```java
void print(List<?> list)
```
어떤 타입의 리스트든 허용한다

#### `<?>`의 특징
읽기 가능, 추가 불가능
```java
Object obj = list.get(0);

list.add("hello"); // X
```

add 안되는 이유
- 컴파일러 입장에서 실제 타입을 알 수 없기 때문
- 타입 안정성이 깨짐

#### Upper Bounded Wildcard
```java
<? extends Number>
```
예시
```java
void print(List<? extends Number> list) {
    for (Number n : list) {
        System.out.println(n);
    }
}

// 가능한 타입
List<Integer>
List<Double>
```
extends는 읽기 전용 느낌
- 실제 타입은 Number 밑의 여러 타입 중 하나
- Integer, Double 등 다양할 수 있기 때문

#### Lower Bounded Wildcard
```java
<? super Integer>
```
예시
```java
void add(List<? super Integer> list) {
    list.add(10);
}
```
Integer의 부모 타입 허용 - Intger, Number, Object 등 <br>

super는 쓰기 전용 느낌
```java
list.add(10);
```
Integer는 자기 자신 또는 부모 타입에 저장 가능
```java
Object obj = list.get(0);
```
하지만 읽어올 때는 실제 타입이 Number인지, Integer인지, Object인지 모르기 때문에 곤란

### PECS
데이터 생산(조회)는 extends <br>
데이터 소비(저장)은 super

### 주요 포인트
| 주제              | 핵심                              |
| --------------- | ------------------------------- |
| Bounded Type    | 타입 범위 제한                        |
| Wildcard 목적     | 불공변성 보완                         |
| `extends`       | 읽기 중심                           |
| `super`         | 쓰기 중심                           |
| PECS            | Producer Extends Consumer Super |
| `<?>` add 불가 이유 | 실제 타입 미확정                       |
| Generic 철학      | 컴파일 타임 타입 안정성                   |

## 3. 제네릭 메서드
제네릭 메서드는 메서드 자체에 타입 파라미터를 선언하는 메서드
- 클래스 전체가 generic 일 수도
- 메서드만 generic 일 수도
기본 형태
```java
public <T> T method(T value) {
    return value;
}
```
- `<T>` 선언 위치가 반환 타입 앞
- 메서드 호출 시 타입 결정

### 제네릭 클래스 vs 제네릭 메서드
#### 제네릭 클래스
```java
class Box<T> {
    T value;
}
```
클래스 전체에서 T 사용 가능

#### 제네릭 메서드
```java
class Util {
    public <T> T identity(T value) {
        return value;
    }
}
```
특정 메서드에서만 T 사용 가능

### 기본 예제
```java
class GenericMethod {

    public <T> T identity(T value) {
        return value;
    }
}

GenericMethod gm = new GenericMethod();

String s = gm.identity("hello");
Integer i = gm.identity(10);
```
컴파일러가 타입을 자동으로 추론

### 제네릭 메서드의 사용 목적
1. 타입 안정성 : 입력과 출력 타입 동일 보장
2. 코드 재사용성 : 하나의 메서드로 여러 타입 처리 가능
3. 타입 연결성 보장 : 입력 타입 = 반환 타입인 것을 컴파일러가 보장

### 제네릭 메서드와 static
#### 일반 제네릭 클래스는 static 사용 불가능
```java
class Box<T> {
    static T value; // ❌
}
```
- static은 클래스 단위
- T는 객체 생성 시 결정 되기 때문


#### static generic method는 가능
```java
class Util {

    public static <T> T identity(T value) {
        return value;
    }
}

String s = Util.identity("hello");
```
메서드 호출 시점에 결정되기 때문에 static과 충돌하지 않음

### Generic Method의 타입 추론 과정
```java
public <T> T identity(T value)

identity("hello")
```
인자 분석 - `"hello"` 를 String으로 판단 - `T = String` - 반환 타입도 String 확정

### Generic Method에서 다양한 타입 사용법
#### 여러 타입 파라미터 사용
```java
public <K, V> void print(K key, V value) {
    System.out.println(key + " : " + value);
}

print("age", 20);
```

#### Bounded Generic Method
```java
public <T extends Number> double sum(T a, T b) {
    return a.doubleValue() + b.doubleValue();
}

sum(10, 20);
sum(1.5, 2.3);

sum("a", "b"); // X
```

### 실무에서 자주 보는 Generic Method
Collections API, Optional, Stram API, static factory method
```java
Collections.sort(List<T>)
Collections.max(Collection<T>)

Optional.of(T value)

<R> Stream<R> map(Function<T, R>)

List.of()
Map.of()
```
문자 인코딩 문제가 발생하기 때문
- Byte Stream : 단순 데이터
- Character Stream : 문자 해석 포함
```
byte → (인코딩/디코딩) → char
```

### 주요 포인트
| 주제                          | 핵심                                  |
| --------------------------- | ----------------------------------- |
| Generic Method              | 메서드 단위 generic                      |
| 타입 추론                       | 컴파일러가 T 추론                          |
| static generic method 가능 이유 | 메서드 호출 시점 타입 결정                     |
| Wildcard 차이                 | wildcard=유연성 / generic method=타입 연결 |
| Bounded Generic Method      | 타입 제한 가능                            |
| Type Erasure                | 런타임 타입 제거                           |
| 오버로딩 제한                     | 소거 후 시그니처 충돌 가능                     |

## 4. Type Erasure (타입 소거)
Type Erasure(타입 소거)는 Java 제네릭의 핵심 구현 방식

### Type Erasure 사용 이유
Java 제네릭은 Java 5에서 추가 되었기 때문
- 이전 버전의 코드
- 이전 버전의 JVM
- 기존 라이브러리와 호환 필요

따라서 컴파일러 수준에서 generic하게 처리하고 런타임에서는 기존 JVM 방식 유지하는 방식 차용

### Erasure의 핵심 동작
컴파일러가 generic 타입 정보를 검사한 뒤 제거
```java
List<String> list = new ArrayList<>();

// 이후 런타임에서는 아래처럼 적용됨
List list = new ArrayList();
```

### 타입 소거 과정
1. 타입 검사 : 컴파일러가 generic 타입 검증
2. 타입 제거 : 컴파일 후 generic 타입 제거
3. 필요한 캐스팅 추가 : 필요한 경우 컴파일러가 자동 캐스팅 삽입

#### 실제 예시
```java
class Box<T> {
    T value;

    T get() {
        return value;
    }
}
```
컴파일 후
```java
class Box {
    Object value;

    Object get() {
        return value;
    }
}
```
- T를 Object로 치환함
- Bounded Type의 경우 최상위 타입으로 소거됨

### Type Erasure로 인해 발생하는 제약들
#### instanceof 제한
```java
if (obj instanceof List<String>) // X
```
런타입에 String 정보가 제거되기 때문에 불가능

#### Generic 배열 생성 불가
배열은 런타임 타입 체크 수행 <br>
generic 타입은 런타임에 제거되기 때문에 불가능

#### Generic Exception 불가
예외처리 또한 런타임 타입 기반 동작
```java
class MyException<T> extends Exception // X
catch (MyException<String>)
```
위 같은 구분이 불가능

#### static T 사용 불가
static은 클래스 단위로 하나만 존재 <br>
그러나 T는 인스턴스마다 달라질 수 있음
```java
class Box<T> {
    static T value; // X
}
```

### Bridge Method
제네릭 + 오버라이딩 시 다형성을 유지하기 위해 컴파일러가 자동 생성
```java
class Parent<T> {
    T get() {
        return null;
    }
}

class Child extends Parent<String> {
    @Override
    String get() {
        return "hello";
    }
}
```
소거 후
```java
// Parent
Object get()

// Child
String get()
```
시그니처가 달라져서 오버라이딩이 깨질 수 있음

```java
Object get() {
    return get();
}
```
컴파일러가 자동으로 Bridge Method를 생성함으로 다형성 유지

### 주요 포인트
| 주제              | 핵심                       |
| --------------- | ------------------------ |
| Type Erasure    | 컴파일 후 generic 제거         |
| 목적              | 하위 호환성                   |
| 소거 방식           | Object 또는 Bound로 치환      |
| 컴파일러 역할         | 타입 검사 + 캐스팅 삽입           |
| 제한 발생 이유        | 런타임 generic 정보 부족        |
| Bridge Method   | 다형성 유지                   |
| Java generic 본질 | compile-time type safety |
